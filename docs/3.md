● Claude Code 开发-测试循环：三层机制

  Claude Code 的开发-测试循环不只靠提示词，而是三层机制的组合：

  ---
  第一层：提示词约束（软约束，可绕过）

  CLAUDE.md 和 .claude/rules/ 中的指令是自然语言规则，依赖模型的指令遵循能力：

  <!-- CLAUDE.md 中的工作流定义 -->
  ### 7阶段流转
  1. brainstorming → 2. using-git-worktrees → 3. writing-plans
  → 4. subagent-driven-development → 5. test-driven-development
  → 6. requesting-code-review → 7. finishing-a-development-branch

  ### 核心铁律
  - TDD 铁律：没有失败测试，不写生产代码。
  - 调试铁律：没有根因调查，不实施修复。
  - 验证铁律：没有运行证据，不声称完成。

  这些是约定，不是强制。模型可能违反（比如跳过测试直接写代码）。

  ---
  第二层：Agent 派发（半自动，结构化）

  规则定义了何时自动使用哪个 Agent，减少人为遗漏：

  <!-- agents.md -->
  ## Immediate Agent Usage
  No user prompt needed:
  1. Complex feature requests → planner agent
  2. Code just written/modified → code-reviewer agent
  3. Bug fix or new feature → tdd-guide agent
  4. Architectural decision → architect agent

  这是半自动的——规则说"No user prompt needed"，但实际执行仍依赖模型主动调用 Agent 工具。它比纯提示词更强，因为：
  - Agent 有独立的系统提示，专注于单一职责
  - 并行派发多个 Agent 可以交叉验证

  ---
  第三层：Hooks 系统（硬约束，可编程）

  hooks.md 提到了真正的程序化拦截机制：

  <!-- hooks.md -->
  ## Hook Types
  - **PreToolUse**: Before tool execution (validation, parameter modification)
  - **PostToolUse**: After tool execution (auto-format, checks)
  - **Stop**: When session ends (final verification)

  Hooks 是 Claude Code 的原生能力，可以在工具调用前后插入自定义逻辑。但当前仓库中没有看到实际的 hook 配置文件（.claude/hooks.json 或类似文件）。

  ---
  实际运作方式

  结合源码和配置，Claude Code 的开发-测试循环是这样运作的：

  ┌───────────┬─────────────────────────────┬────────────────────────┬─────────────────┐
  │    层     │            机制             │         强制力         │     可审计      │
  ├───────────┼─────────────────────────────┼────────────────────────┼─────────────────┤
  │ CLAUDE.md │ 自然语言指令                │ 软（模型可忽略）       │ 是（文件可见）  │
  ├───────────┼─────────────────────────────┼────────────────────────┼─────────────────┤
  │ Agents    │ 专用子代理派发              │ 中（结构化但依赖调用） │ 是（日志可见）  │
  ├───────────┼─────────────────────────────┼────────────────────────┼─────────────────┤
  │ Hooks     │ PreToolUse/PostToolUse 拦截 │ 硬（代码级）           │ 是（hook 输出） │
  ├───────────┼─────────────────────────────┼────────────────────────┼─────────────────┤
  │ CI/CD     │ 外部流水线                  │ 硬（不可绕过）         │ 是（CI 日志）   │
  └───────────┴─────────────────────────────┴────────────────────────┴─────────────────┘

  关键洞察：

  1. 提示词是"宪法"，定义了理想流程（TDD、代码审查、验证）
  2. Agents 是"法院"，将抽象规则具象化为可执行的检查
  3. Hooks 是"警察"，在关键节点强制执行（但当前配置较少）
  4. CI 是"最高法院"，是最后的硬性门禁

  你之前的 flaky 测试问题恰好说明了这个体系的盲点：提示词规定了"验证铁律"，但如果测试本身不稳定，即使严格执行了流程，结果也不可靠。这就是为什么加固测试基础设施比添加更多规则更优先。
