● 问题描述

  项目：MiCode（TypeScript CLI AI 助手），inline 模式渲染（非 alt-screen）。

  现象：流式输出期间，终端累积几十份完整消息副本。每份副本包含完整的 streaming 内容 + footer（状态栏、输入框）。无鼠标操作时 3-4 次，鼠标选区时几十上百次，ESC 无法中断。

  已排除：
  - handleUserSubmit 重复调用（日志证明只调用一次）
  - streamingQuery 重复执行（日志证明只执行一次）
  - appendStreamingMarkdown 重复 finalize（日志证明只 finalize 一次）

  已确认：问题在渲染层。useEffect 运行 ~1400 次，92.6% 的 commit 有 newLines=0（无新固化行）。

  根因链

  每个 token → messagesStore.updateStreaming() → 创建新 messages 数组引用
  → useEffect 依赖数组包含 messages → effect 重跑
  → InlineRenderer.commit() 写 stdout（~1,108 字节 ANSI）
  → 但 newLines=0、streamingLines 未变、footer 未变
  → 纯粹的重复写入，终端累积副本

  核心问题：commit() 没有"内容未变则跳过"的机制。即使帧内容完全相同，仍然执行完整的 erase-rewrite 周期。

  修复方案

  在 InlineRenderer.commit() 入口做帧级快照比较：

  // 缓存上一帧
  private prevSnapshot: { newLinesLen: number; streamingLines: string[]|null; footerLines: string[] }|null = null;

  commit(frame: CommitFrame): void {
    const footerLines = frame.footer.lines;
    const snap = this.prevSnapshot;
    const unchanged = snap
      && frame.newLines.length === 0
      && frame.streamingLines === null
      && snap.streamingLines === null
      && !frame.transitions.justFinalized
      && !frame.transitions.needEraseDraft
      && !frame.transitions.forceFooterReset
      && !frame.prefix
      && snap.footerLines.length === footerLines.length
      && snap.footerLines.every((l, i) => l === footerLines[i]);

    if (unchanged) return; // 跳过

    this.prevSnapshot = {
      newLinesLen: frame.newLines.length,
      streamingLines: frame.streamingLines,
      footerLines: [...footerLines],
    };
    // ... 原有 commit 逻辑
  }

  为什么不破坏状态栏/输入框：
  - 状态栏变化 → footer.lines 不同 → 不跳过
  - 输入框变化 → footer.lines 不同 → 不跳过
  - 流式内容变化 → streamingLines 不为 null → 不跳过
  - 纯 token 到达（内容未变）→ 全部相同 → 跳过

  这是一个无限循环，退出条件完全依赖循环体内部的 return 语句和 continue 跳转。

  问题 2：LLM 一直调工具不收尾时怎么处理？

  没有"软上限 + hint"机制。 但有多个独立的保护层：

  2a. Token Budget（+500k 机制）

  用户在 prompt 中写 +500k 或 use 2M tokens 时，系统解析为 token 预算（src/utils/tokenBudget.ts）。

  检查逻辑在 src/query/tokenBudget.ts:45-93：

  export function checkTokenBudget(
    tracker: BudgetTracker,
    agentId: string | undefined,
    budget: number | null,
    globalTurnTokens: number,
  ): TokenBudgetDecision {
    if (agentId || budget === null || budget <= 0) {
      return { action: 'stop', completionEvent: null }
    }
    // ...
    if (!isDiminishing && turnTokens < budget * COMPLETION_THRESHOLD) {
      // 还没用到 90%，继续
      return { action: 'continue', nudgeMessage: getBudgetContinuationMessage(...) }
    }
    // 达到 90% 或收益递减，停止
  }

  nudge 消息内容（src/utils/tokenBudget.ts:72）：

  `Stopped at ${pct}% of token target (${fmt(turnTokens)} / ${fmt(budget)}). Keep working — do not summarize.`

  这是唯一类似"hint"的机制，但它不是基于轮次，而是基于 token 消耗量。在 src/query.ts:1308-1341 中应用：

  if (feature('TOKEN_BUDGET')) {

        messages: [...messagesForQuery, ...assistantMessages,
          createUserMessage({ content: decision.nudgeMessage, isMeta: true })],
        // ...
        transition: { reason: 'token_budget_continuation' },
      }
      continue
    }
  }

  src/QueryEngine.ts:972：

  if (maxBudgetUsd !== undefined && getTotalCost() >= maxBudgetUsd) {
    yield { type: 'result', subtype: 'error_max_budget_usd', ... }

  问题 3：max_tokens 截断恢复和轮次上限是两个独立机制吗？

  是的，完全独立。

  max_output_tokens 恢复

  定义在 src/query.ts:164：

  const MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3

  恢复逻辑在 src/query.ts:1188-1256，分两阶段：

  1. Escalation（一次性）：从默认 8k 提升到 64k（ESCALATED_MAX_TOKENS），直接重试同一请求，不注入消息
  2. Multi-turn recovery（最多 3 次）：注入恢复消息：

  const recoveryMessage = createUserMessage({
    content: 'Output token limit hit. Resume directly — no apology, no recap of what you were doing. ' +
      'Pick up mid-thought if that is where the cut happened. Break remaining work into smaller pieces.',
    isMeta: true,
  })

  恢复计数器 maxOutputTokensRecoveryCount 在每轮工具执行后重置为 0（src/query.ts:1721），所以每轮最多 3 次恢复。

  maxTurns 轮次上限

  在循环末尾检查（src/query.ts:1705），触发时直接 return { reason: 'max_turns' }，不尝试恢复。

  两个机制的 state 字段完全独立：
  - maxOutputTokensRecoveryCount — max_tokens 恢复计数
  - turnCount — 轮次计数
  - transition — 记录上一次 continue 的原因（用于调试）

  问题 4：stop_reason 处理逻辑

  核心结论：不依赖 stop_reason 决定是否继续循环，而是检查 content 中的 tool_use 块。

  src/query.ts:554 的注释明确说明：

  // Note: stop_reason === 'tool_use' is unreliable -- it's not always set correctly.
  // Set during streaming whenever a tool_use block arrives — the sole
  // loop-exit signal. If false after streaming, we're done (modulo stop-hook retry).
  const toolUseBlocks: ToolUseBlock[] = []
  let needsFollowUp = false

  在流式处理中（src/query.ts:829-834）：

  if (message.type === 'assistant') {
    assistantMessages.push(message)
    const msgToolUseBlocks = message.message.content.filter(
      content => content.type === 'tool_use',
    ) as ToolUseBlock[]
    if (msgToolUseBlocks.length > 0) {
      toolUseBlocks.push(...msgToolUseBlocks)
      needsFollowUp = true
    }
  }

  循环决策在 src/query.ts:1062：

  if (!needsFollowUp) {
    // 没有 tool_use 块 → 处理 max_output_tokens 恢复、stop hooks、token budget
    // 最终 return { reason: 'completed' }
  }
  // 否则 → 执行工具 → 继续循环

  stop_reason 的实际用途： 仅用于诊断和结果报告（src/QueryEngine.ts:766-807），不影响循环控制流：

  // Capture stop_reason from message_delta. The assistant message
  // is yielded at content_block_stop with stop_reason=null; the
  // real value only arrives here.
  if (message.event.delta.stop_reason != null) {
    lastStopReason = message.event.delta.stop_reason
  }

  lastStopReason 最终传入 result.stop_reason 给调用方，仅作报告用。

  问题 5：主循环返回值

  返回结构化对象，不是字符串。

  query() 函数的返回类型（src/query.ts:227）：

  export async function* query(
    params: QueryParams,
  ): AsyncGenerator<
    | StreamEvent
    | RequestStartEvent
    | Message
    | TombstoneMessage
    | ToolUseSummaryMessage,
    Terminal  // ← 返回类型
  >

  Terminal 类型（从 src/query/transitions.js 导入，实际定义在 src/query.ts 的各个 return 语句中）是一个 discriminated union：

  // 所有可能的返回值：
  { reason: 'completed' }
  { reason: 'max_turns', turnCount: number }
  { reason: 'aborted_streaming' }
  { reason: 'aborted_tools' }
  { reason: 'blocking_limit' }
  { reason: 'prompt_too_long' }
  { reason: 'model_error', error: unknown }
  { reason: 'image_error' }
  { reason: 'stop_hook_prevented' }
  { reason: 'hook_stopped' }

  QueryEngine 层的处理（src/QueryEngine.ts:842-874）：

  收到 max_turns_reached attachment 后，yield 结构化的 SDK result：

  yield {
    type: 'result',
    subtype: 'error_max_turns',
    is_error: true,
    num_turns: message.attachment.turnCount,
    stop_reason: lastStopReason,
    total_cost_usd: getTotalCost(),
    errors: [`Reached maximum number of turns (${message.attachment.maxTurns})`],
    // ... 其他字段
  }

  对比你的实现： return 'Loop ended: maximum turns reached' 这个占位字符串是对真实行为的严重简化。真实实现：
  1. yield 一个 max_turns_reached attachment 消息（给 UI/SDK）
  2. yield 一个结构化的 error_max_turns result（含 stop_reason、usage、cost 等完整元数据）
  3. 返回 { reason: 'max_turns', turnCount } 给内部调用链
