# mi-code 工具执行路径差异审计

日期：2026-07-31

## 1. 审计问题

本审计只回答：

> mi-code 中，一个模型工具调用从出现到执行完成有几条路径；每条路径是否经过输入校验、权限、Hook、执行、输出处理和错误恢复？

执行路径按两层计数：

1. **执行引擎**：真正把输入交给 executor 的代码。
2. **运行时装配**：主代理和不同子代理如何给执行引擎注入权限、Hook 与恢复能力。

当前共有 **4 套执行引擎**，默认生产图中至少有 **4 种安全语义**。

## 2. 执行引擎

| ID | 执行引擎 | 最终调用 | 默认生产可达 | 权限 | Hook |
|---|---|---|---:|---|---|
| E1 | `StreamingToolExecutor.executeTool()` | `ToolRegistry.execute()` | 是 | 可选 RuntimeGate 或 legacy checker | 无 |
| E2 | `streamingQuery()` 串行回退 | `ToolRegistry.execute()` | API 可达，主入口默认关闭 | 独立的 `checkPermissionOrBlock()` | 无 |
| E3 | 旧 `agentLoop()` | `ToolRegistry.execute()` | 主入口不可达，但仍公开导出 | 无 | 仅串行 batch 有 Pre/Post |
| E4 | `runWithVercelAI()` | 直接调用 executor | 子代理兼容回退 | 可选 checker | 无 |

源码调用点：

- `src/agent/streaming-executor.ts:164`
- `src/agent/streaming-executor.ts:197`
- `src/agent/streaming-query.ts:819`
- `src/agent/loop.ts:265`
- `src/agent/loop.ts:293`
- `src/agent/llm-vercel.ts:61` 直接调用 executor，绕过 Registry

### E1 的三种语义

同一个 `StreamingToolExecutor` 会因构造参数不同产生三种行为：

- checker + RuntimeGate：`allow/deny/ask` 全部执行。
- 只有 checker：只阻断 `deny`，`ask` 静默放行。
- 两者都没有：直接执行。

因此共用一个 class 不等于共用一个安全执行边界。

### E2 复制权限流程

关闭流式执行后，`streamingQuery()` 不调用 E1，而是：

```text
checkPermissionOrBlock()
→ RuntimeGate.authorize() 或 legacy checker
→ registry.execute()
```

这与 E1 的 `RuntimeGate.execute(decision, executor)` 是两份权限实现。

### E3 是危险遗留入口

旧 `agentLoop()`：

- 并行只读 batch 没有权限，也没有 Hook。
- 串行 batch 有 Pre/Post Hook，但没有 PermissionChecker。
- 仍从 `src/agent/index.ts` 公开导出。

### E4 语义再次分叉

Vercel 回退路径：

- 使用 AI SDK `jsonSchema()`。
- 直接调用 executor，不经过 Registry。
- checker 的 `ask` 在没有回调时默认拒绝。

这与 E1/E2 legacy 分支的“ask 放行”相反。

## 3. 默认生产运行时矩阵

符号：

- ✅：明确经过。
- ❌：明确不经过。
- △：存在但语义不完整。

| 路径 | 调用链 | Runtime 校验 | 权限 | Pre | Post | 结构化结果 |
|---|---|---:|---:|---:|---:|---:|
| P1 主代理流式 | `index → streamingQuery → E1` | ❌ | ✅ RuntimeGate | ❌ | △ UI observer | △ ask 专用侧信道 |
| P2 `spawn_agent` | `spawn_agent → runSubagent → E1` | ❌ | △ checker，ask 放行 | ❌ | ❌ | △ legacy 状态前缀 |
| P3 `task` | `task → runSubagent → E1` | ❌ | ❌ | ❌ | ❌ | ❌ 只返回文本 |
| P4 自组织子代理 | `spawn_self_organizing → E1` | ❌ | △ checker，ask 放行 | ❌ | ❌ | ❌ 后台文本 |
| P5 主串行回退 | `streamingQuery(enable=false) → E2` | ❌ | ✅/△ | ❌ | △ UI observer | △ ask 专用侧信道 |
| P6 Vercel 回退 | 子代理无 client → E4 | △ AI SDK schema | △ 各调用方不同 | ❌ | ❌ | ❌ |
| P7 旧循环 | 外部调用 E3 | ❌ | ❌ | △ 仅串行 | △ 仅串行 | ❌ |

## 4. P1：主代理默认流式路径

```text
src/index.ts
→ streamingQuery()
→ StreamingToolExecutor.addTool()
→ executeTool()
→ PermissionChecker.checkDecision()
→ RuntimeSecurityGate.execute()
→ ToolRegistry.execute()
→ RegisteredTool.executor()
→ tool_result
→ index.ts PostToolUse UI 通知
```

事实：

- `src/index.ts:829-836` 同时传 checker 和 RuntimeGate。
- provider 返回的 `block.input` 被直接当作
  `Record<string, unknown>`。
- E1 和 Registry 没有独立 runtime schema validation。
- `src/index.ts:138-141` 注册了 HookRunner，但没有传入 E1。
- PreToolUse 不触发。
- `src/index.ts:899-908` 的 PostToolUse 在 tool result 形成后运行，只向 UI
  输出 message，不能修改写回模型的结果。
- Registry 把 executor throw 转成普通错误字符串。

## 5. P2：spawn_agent 子代理

```text
spawn_agent
→ runSubagent()
→ runSubagentWithClient()
→ streamingQuery()
→ E1
```

事实：

- `src/index.ts:214-223` 给 `spawn_agent` 注入 checker。
- `src/agent/subagent.ts:411-420` 没有给子循环传 RuntimeGate。
- 子代理因此进入 E1 legacy 分支：deny 阻断，ask 放行。
- 子代理内部工具调用不触发主 HookRunner。
- CompletionContract 和 delegation gate 虽有代码，但主入口没有启用。

## 6. P3：task 子代理

```text
task
→ runSubagent()
→ runSubagentWithClient()
→ streamingQuery()
→ E1
```

事实：

- `src/index.ts:200` 创建 task tool 时没有传 checker。
- `src/agent/tools/task-tool.ts` 调用 `runSubagent()` 时也没有传 checker。
- 外层 task 审批后，子代理内部工具调用没有任何 PermissionChecker。
- task 丢弃 `SubagentResult` 的 status/evidence，只返回文本。

这是当前最严重的生产可达权限旁路。

## 7. P4：自组织子代理

事实：

- 主入口给自组织代理注入 checker 和 client。
- 子循环没有 RuntimeGate。
- ask 静默放行。
- 启动工具立即返回，后台最终完成或失败不进入统一 tool result。
- 后台错误主要写 stderr。

因此：

```text
dispatch accepted ≠ execution completed ≠ verification passed
```

## 8. ToolRegistry 不是安全边界

`src/agent/tool-registry.ts:68-84` 只负责：

1. 按名称查找工具。
2. 调用 executor。
3. 把异常转成字符串。

它不负责：

- runtime schema validation；
- Hook；
- PermissionChecker；
- RuntimeGate；
- cancellation；
- structured outcome；
- evidence 或 ledger。

E1/E2/E3 都调用 Registry，并没有因此获得一致语义；E4 还完全绕过它。

## 9. 输入校验缺口

当前没有一个位置能保证：

```text
原始输入
→ schema validation
→ tool-specific validation
→ Pre updatedInput
→ 完整重新验证
→ 对最终输入做权限判断
→ 执行同一份最终输入
```

部分 executor 自行校验，部分只做 TypeScript cast。provider schema 不能作为
mi-code 自己的安全边界。

## 10. Hook 接线差异

| 事件 | 已注册 | 主生产路径 | 子代理内部 | 旧 loop |
|---|---:|---:|---:|---:|
| SessionStart | ✅ | ✅ | ❌ | N/A |
| PreToolUse | ✅ | ❌ | ❌ | △ 仅串行 |
| PostToolUse | ✅ | △ UI observer | ❌ | △ 仅串行 |
| Stop | 不支持 | ❌ | ❌ | ❌ |

HookRunner 当前“存在但不在生产执行边界内”。

## 11. 输出和错误缺口

`ToolExecutor` 固定返回 `Promise<string>`，`ToolResultBlock` 只有字符串。

不能原生表达：

- success/failure/blocked/cancelled/timeout；
- exit code；
- 最终输入；
- permission 或 Hook 决策；
- dispatch/completion；
- evidence。

Registry 又把异常提前转成字符串，导致上层不能可靠区分“成功输出含 Error”
与“执行失败”。

## 12. 其他设施

### dispatch-map

`src/agent/dispatch-map.ts` 是第二套工具定义和实现，当前只有测试使用。未来若
重新接入，会绕过现有权限和进程执行演进。

### MCPRouter

MCPRouter 能直接 `client.callTool()`，但当前主入口没有装配。未来接入必须进入
统一执行边界。

### 直接 executor

内部代码和测试可以直接调用 `tool.executor(input)`。模块 API 目前无法从类型上
强制所有执行经过安全入口。

## 13. 缺口分级

### H0：改变实现方向

1. 没有唯一执行边界。
2. 没有独立 runtime 输入校验。
3. 字符串结果不能支撑验证账本。

### H1：安全与一致性

4. task 子代理没有 checker。
5. spawn_agent 和自组织子代理 ask 静默放行。
6. 主生产路径没有 PreToolUse。
7. 子代理内部没有 Hook。
8. 主 PostToolUse 只是 UI observer。
9. E1/E2 重复权限实现。
10. E4 ask 语义不同。

### H2：生命周期与审计

11. 通用 ToolExecutionContext 没有实际 cancellation 契约。
12. 没有结构化工具状态。
13. 后台 completion 不进入统一结果。
14. CompletionContract 和 delegation gate 未在主入口启用。
15. transcript checkpoint 只验证配对，不验证执行成功。

### H3：遗留旁路

16. 旧 agentLoop 仍公开导出。
17. dispatch-map 是第二套工具实现。
18. MCP 未来可能形成新旁路。
19. executor 可被内部调用方直接调用。

## 14. 三条硬约束

### A. 一个受控入口

主代理、串行回退和所有子代理必须汇聚。仅“都调用 Registry”不够，因为
Registry 当前不是策略边界。

### B. 同一份最终输入

必须能证明：

```text
validated(finalInput)
permissionDecision.input == finalInput
executorInput == finalInput
```

Pre 修改输入后必须完整重验，再做权限决策。

### C. 结构化执行事实

验证账本必须记录真实 execution outcome，不能通过搜索 transcript 中是否出现
`npm test` 等文本进行推断。

## 15. 结论

当前状态不是“一条主路径加几个小旁路”，而是：

```text
4 套执行引擎
× 多种依赖装配
= 至少 4 种默认生产安全语义
  + 3 种兼容/遗留语义
```

后续设计必须先统一 P1-P5 的执行边界，再叠加 Hook 生命周期和验证账本。
