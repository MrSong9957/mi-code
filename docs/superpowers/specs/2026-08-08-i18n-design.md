# MiCode 国际化设计

- 日期：2026-08-08
- 状态：设计阶段，待审核
- 范围：MiCode 用户体验语言、静态 CLI/TUI 文案与 Agent 默认回复语言偏好

## 1. Goals

本设计为 MiCode 建立轻量、可测试、可运行时切换的国际化基础设施：

- 支持 zh-CN 与 en-US。
- 默认语言固定为 zh-CN，不读取操作系统 locale、LANG 或 LC_ALL。
- 覆盖当前代码中已确认的用户可见静态 CLI/TUI 文本。
- 支持启动参数临时覆盖，以及 /language 运行时持久化切换。
- 让 React/Ink 与普通 TypeScript 读取同一个 runtime language 状态。
- 让下一轮 Agent 请求使用最新的自然语言回复偏好。
- 不引入第三方 i18n 库，并为第三种语言保留不修改业务代码的扩展路径。

## 2. Non-goals

首版不做：

- 自动检测系统语言。
- 翻译已有 transcript、用户原始输入、Agent 原文或工具输出。
- 翻译代码、diff、路径、模型 ID、Provider、命令名、工具名、参数和协议字段。
- 对 Agent 输出做本地翻译。
- 全量翻译 src/prompts/system.md 或 src/prompts/planner.md。
- ICU MessageFormat 或完整 plural engine。
- 第三方 i18n 库。
- 自定义 AST lint 作为首版英文残留检查器。
- LanguageController 抽象；/language handler 直接编排持久化和 runtime 更新。

### 3.6 Agent 回复语言偏好

system.md 和 planner.md 不做全量翻译。

`/language` 是 MiCode 固定 UI 语言的硬性控制：所有受 locale 管理的 CLI/TUI 静态文案使用当前 locale。每轮 system prompt 构造时，根据当前 runtime language 追加一个默认回复语言偏好：

- zh-CN：默认使用简体中文回答自然语言内容。
- en-US：默认使用英文回答自然语言内容。

该偏好是给模型的软约束，模型不保证一定遵守；用户明确指定的回复语言和项目规则优先于默认偏好。它不对模型生成内容、用户原始输入或工具原始输出执行本地翻译，也不改变命令、工具、代码、路径、模型 ID、协议字段和文件名的原样要求。

## 4. Architecture

### 4.1 职责分层

~~~text
ConfigStore
  负责 language 的读取和持久化

LanguageStore
  负责当前进程的 runtimeLanguage

translator
  根据同一个 LanguageStore 在调用时查找翻译

LocaleProvider/useLocale
  让 React/Ink 组件订阅同一个 LanguageStore
~~~

ConfigStore 不作为 React 状态源，LocaleProvider 不保存第二份语言状态。

### 4.2 目录结构

~~~text
src/locale/
  types.ts
  language-store.ts
  translator.ts
  context.tsx
  resources/
    zh-CN.ts
    en-US.ts
  index.ts
~~~

职责：

- types.ts：语言类型、默认语言、支持语言和翻译相关类型。
- language-store.ts：Zustand vanilla LanguageStore 创建和状态接口。
- translator.ts：资源查找、参数插值和 fallback。
- context.tsx：LocaleProvider、useLocale()、useLanguage()。
- resources/*.ts：按语言拆分、按领域命名空间组织的资源。
- index.ts：locale 模块统一导出。

不建立模块级 singleton。应用入口创建唯一 LanguageStore，并把它传给 bootstrap、React provider、命令执行上下文和 Agent prompt 构造链路。

## 5. Runtime language and lifecycle

### 5.1 支持语言

首版支持 zh-CN 和 en-US，默认值固定为 zh-CN。

语言校验必须由统一的 isLanguage 或等价函数完成，并复用于 CLI、ConfigStore 读取和 /language 参数。

### 5.2 启动初始化

~~~text
runtimeLanguage =
  validCliLanguage
  ?? validConfigLanguage
  ?? 'zh-CN'
~~~

规则：

- --language 只决定本次进程初始语言，不写入 ConfigStore。
- 非法 ConfigStore.language 视为未配置；缺少 language 字段的旧配置也视为未配置并在内存中使用 zh-CN。
- 仅因旧配置缺少 language 或值非法而使用默认语言时，不自动改写 config.json。
- `micode --language <unsupported>` 是显式用户输入错误：显示支持的 zh-CN / en-US，非零退出，不静默回退到 ConfigStore 或 zh-CN。
- 不读取 OS locale、LANG 或 LC_ALL。
- 启动完成后，runtimeLanguage 由 LanguageStore 独立维护。
- 启动后不反复从 ConfigStore 读取当前运行语言。

### 5.3 /language 运行时切换

~~~text
校验参数
  ↓
ConfigStore 持久化
  ↓ 成功
LanguageStore.setLanguage(lang)
  ↓
使用新语言生成成功反馈
~~~

具体语义：

- 无参数 `/language`：只显示当前 effective language 和支持的语言列表，反馈使用当前语言；不写 ConfigStore，不修改 LanguageStore。
- 无效语言：不写配置、不更新 LanguageStore，使用旧语言报错。
- 持久化失败：不更新 LanguageStore，使用旧语言报错。
- 持久化成功：更新 LanguageStore，后续进程行为使用新语言。
- 成功反馈在 LanguageStore 更新后生成，因此使用新语言。
- 旧 transcript 不重写。

当前命令执行器存在 ConfigStore 路径和 CommandContext 路径。/language 接入已有配置命令流程，不能创建第二个命令分发体系。

### 5.4 生效时机

立即生效：

- React/Ink 静态 UI 在 LanguageStore 更新后自动重渲染。
- 下一条命令反馈读取新语言。
- 后续 spinner 状态文本和新产生的摘要读取新语言。

不追溯修改：

- 已输出的 transcript。
- 用户输入、Agent 原文、工具输出和历史消息。

下一轮生效：

- Agent system prompt 的语言偏好。
- 新建的 Agent 请求和子 Agent 请求。

当前正在执行的 Agent 请求保持已创建的 system prompt，不因语言切换而中断或重写。

## 6. Resource and key design

### 6.1 资源组织

资源按语言拆分，文件内部按领域命名空间组织：

~~~text
resources/zh-CN.ts
resources/en-US.ts
~~~

领域建议：

~~~text
common
commands
status
spinner
overlay
permission
tool
session
errors
agent
~~~

当前规模不拆成领域/语言多层目录；资源增长后可以内部拆分而不改变调用 API。

### 6.2 key 命名

key 使用稳定的语义命名：

~~~text
领域.对象.动作或状态
~~~

示例：

~~~text
common.cancel
commands.help.title
commands.language.invalid
commands.language.switched
permission.dialog.title
permission.option.allowOnce
overlay.askQuestion.submit
overlay.planApproval.continue
status.thinking
spinner.verb.analyzing
tool.search.noMatches
tool.search.result.one
tool.search.result.other
session.resume.hint
errors.apiKeyMissing
~~~

禁止把完整英文句子、参数值或标点格式编码进 key。

### 6.3 canonical resource 和 TranslationKey

zh-CN 是 canonical resource/schema：

- TranslationKey 从 zh-CN 资源的叶子节点自动推导。
- 不手工维护第二套完整 key union。
- en-US 使用由 zh-CN 结构派生的同形约束。
- 新增语言只需提供满足相同 resource shape 的文件并注册语言。

TypeScript 负责：

- 缺少必需 key 时失败。
- 资源节点层级不一致时失败。
- 资源值不是字符串或合法命名空间时失败。
- 如果实际 TypeScript 类型实现无法拒绝 extra key，再由资源完整性测试补充检查；若 TypeScript 已能拒绝，则不重复运行完整 key 集合比较。

### 6.4 参数和数量

translator 提供：

~~~text
t(key, params?: Record<string, string | number>)
~~~

资源使用 {param} 占位符。

不实现 ICU 或完整 plural engine。英文单复数使用显式 key：

~~~text
tool.search.result.one
tool.search.result.other
~~~

参数集合由测试比较，确保两个语言资源拥有相同占位符名称。

## 7. React and non-React access

### 7.1 React/Ink

LocaleProvider 订阅传入的 LanguageStore，并将当前语言和 translator 暴露给 useLocale()。

Provider 可以像现有 ThemeStoreProvider 一样作为 bootstrap 装配层，但不能自己保存另一份可写语言状态。LanguageStore 是唯一状态源。

React 组件在 render 阶段调用 t()。不得在模块初始化阶段生成依赖当前语言的最终字符串。

### 7.2 普通 TypeScript

普通 TypeScript 模块通过绑定同一个 LanguageStore 创建 translator：

~~~text
translator.t(key, params)
  每次调用读取 languageStore.getState().language
~~~

适用范围包括：

- 命令执行器。
- 工具/询问/子代理 presentation builder。
- 错误和会话提示构造。
- 每轮 Agent system prompt 构造。

### 7.3 禁止的缓存模式

禁止：

~~~text
模块加载时读取当前语言并生成 const helpText
创建 translator 时固定绑定 zh-CN 并永久复用最终字符串
~~~

允许：

~~~text
模块加载时加载静态资源表
调用 t() 时读取当前 LanguageStore
组件每次 render 时调用 t()
~~~

## 8. Permission stable-ID migration

权限确认是 locale 化中的安全边界。

当前代码存在“用户可见 label 同时作为决策映射值”的耦合，例如 Allow once 等字符串被用于精确判断。翻译后不能继续依赖这些字符串。

设计要求：

- 每个权限选项拥有稳定的内部 decision ID。
- UI 使用当前语言资源渲染 label 和 description。
- outcome 到 UserDecision 的映射只读取稳定 ID，不读取翻译后的文本。
- Reject、未知值、空值、取消和非 submitted outcome 仍遵循现有安全拒绝语义。
- 业务逻辑、持久化协议和安全判断不得依赖翻译文本。

示例：

~~~text
decision ID: approved_once
zh-CN label: 仅允许一次
en-US label: Allow once
~~~

稳定 ID 不属于用户体验语言，不进入 locale 翻译。

## 9. Agent prompt behavior

不翻译完整 system.md/planner.md。

每次用户提交并开始构造新请求时：

1. 从 LanguageStore 读取当前语言。
2. 构造当前 turn 的 system prompt。
3. 追加对应的默认自然语言回复偏好。
4. 将该 prompt 快照传给当前请求。

语言偏好只影响 Agent 默认自然语言回复，是软约束而非模型输出翻译或强制保证；`/language` 对 MiCode 固定 UI locale 的切换仍是硬性要求。不影响：

- 用户原始输入。
- 代码和 diff。
- 路径、命令、参数和工具名。
- Provider、模型 ID 和协议字段。
- 工具输出和 Agent 已生成的历史内容。

用户明确要求的回复语言和项目规则优先于默认语言偏好。

## 10. Fallback and error behavior

### 10.1 translator fallback

翻译查找顺序固定为：

~~~text
当前语言资源
  ↓ 缺失
zh-CN 资源
  ↓ 仍缺失
‹missing translation: key›
~~~

生产环境单个翻译缺失不得让 CLI/TUI 崩溃，也不得因为 React render 中的缺失 key 抛出未处理异常。

最终 marker 必须包含 key，不能静默返回空字符串。

### 10.2 开发和测试职责

fallback 只保证生产稳定，不负责证明资源完整。

开发/测试阶段必须通过 TypeScript shape 检查和资源测试暴露：

- 缺少 key。
- 占位符集合不一致。
- 非法资源节点。

只有在实际 TypeScript 类型实现无法拒绝 extra key 时，资源测试才额外检查 key 集合；不得为同一完整性契约无条件维护两套检查。

生产 fallback 不能掩盖开发阶段漏翻译。

## 12. Testing strategy

测试只保护不同层级的核心契约，避免重复测试同一行为。

### 12.1 Language validation

验证：

- zh-CN、en-US 合法。
- 未知值非法。
- 缺失 language 的旧配置和非法 ConfigStore.language 视为未配置，内存使用 zh-CN，且启动不自动改写 config.json。
- 合法 CLI language 优先于合法 ConfigStore.language。
- 非法 CLI language 显示支持的 zh-CN / en-US，并以非零状态退出，不回退到配置或默认语言。
- CLI、ConfigStore 和 /language 使用一致校验规则。

### 12.2 Resource shape and placeholders

TypeScript 检查 canonical shape。

测试补充验证：

- 占位符名称集合一致。
- 只有 TypeScript 无法拒绝 extra key 时，才比较资源叶子 key 集合。
- 新增语言复用同一 shape 和 placeholder 完整性检查。

### 12.3 Translator

验证：

- 基础 key 查找。
- {param} 插值。
- .one/.other 资源调用。
- 当前语言缺失时回退 zh-CN。
- 两层资源都缺失时返回 marker，不抛异常。
- 缺少插值参数不会抛异常、不替换为空字符串，并保留原 `{param}` 占位符；测试必须能识别该情况。
- 正常资源不得带着缺失插值参数进入发布；开发/测试验证负责阻止该问题。

### 12.4 LanguageStore and React subscription

验证：

- 初始语言正确。
- setLanguage() 更新唯一 runtime 状态。
- 订阅者收到变化。
- React 组件从中文切换到英文后重新渲染。
- Context 未保存第二份可写语言状态。

### 12.5 /language semantics

验证：

- 合法语言先持久化，成功后才更新 store。
- 成功反馈使用新语言。
- 无参数 `/language` 只显示当前 effective language 和支持语言，不写配置、不更新 store，反馈使用旧的当前语言。
- 参数非法时不写配置、不更新 store，错误使用旧语言。
- 持久化失败时不更新 store，错误使用旧语言。
- 已有 transcript 不重写。

### 12.6 Agent prompt

至少验证：

- zh-CN 请求包含中文默认回复偏好。
- en-US 请求包含英文默认回复偏好。
- 语言切换后下一轮请求读取新语言。
- 当前请求继续使用已创建的旧 prompt。
- 命令、工具、协议、代码和路径约束保持原样。

### 12.7 Restricted English audit

实现完成后，对已定义的用户可见模块执行限定范围搜索，由 Agent 对命中进行分类：

- 用户可见硬编码：必须迁移到 locale。
- 合法技术英文：明确记录原因并保留。
- 动态原始内容：不迁移。

不对全仓库执行粗暴英文正则，也不把测试 fixture、协议字段和代码视为漏翻译。

## 13. Acceptance criteria

设计实现完成后，必须满足：

1. 默认语言始终为 zh-CN，不读取 OS locale。
2. --language 只影响当前进程初始语言，不写 ConfigStore。
3. 非法 CLI language 是显式输入错误，显示支持语言并以非零状态退出；非法配置值按未配置处理且不自动改写 config.json。
4. 无参数 /language 只显示当前 effective language 和支持语言，不写配置、不更新 runtime，反馈使用当前语言。
5. /language <lang> 严格遵循“校验 → 持久化 → 更新 runtime → 新语言反馈”。
6. CLI、TUI、权限/计划审批、工具摘要、询问摘要、子代理摘要和错误包装的静态文本可切换。
7. React 与普通 TypeScript 读取同一个 LanguageStore。
8. 不存在模块初始化阶段缓存的最终翻译字符串。
