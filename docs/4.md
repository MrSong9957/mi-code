  1.4 串行 vs 并行决策

  toolOrchestration.ts:91-116 的 partitionToolCalls() 实现了分区逻辑：

  // src/services/tools/toolOrchestration.ts:91-116
  function partitionToolCalls(toolUseMessages, toolUseContext): Batch[] {
    return toolUseMessages.reduce((acc, toolUse) => {
      const tool = findToolByName(toolUseContext.options.tools, toolUse.name)
      const parsedInput = tool?.inputSchema.safeParse(toolUse.input)
      const isConcurrencySafe = parsedInput?.success
        ? Boolean(tool?.isConcurrencySafe(parsedInput.data))
        : false
      if (isConcurrencySafe && acc[acc.length - 1]?.isConcurrencySafe) {
        acc[acc.length - 1]!.blocks.push(toolUse)  // 合并到同一批次
      } else {
        acc.push({ isConcurrencySafe, blocks: [toolUse] })  // 新批次
      }
      return acc
    }, [])
  }

  规则：
  - 连续的 isConcurrencySafe=true 工具合并为一个并行批次（最多 10 个并发，CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY）
  - 任何 isConcurrencySafe=false 的工具独占一个串行批次
  - 批次之间严格按顺序执行

  StreamingToolExecutor（src/services/tools/StreamingToolExecutor.ts:40）有相同的并发控制：

  // src/services/tools/StreamingToolExecutor.ts:129-135
  private canExecuteTool(isConcurrencySafe: boolean): boolean {
    const executingTools = this.tools.filter(t => t.status === 'executing')
    return (
      executingTools.length === 0 ||
      (isConcurrencySafe && executingTools.every(t => t.isConcurrencySafe))
    )
  }

  // src/utils/claudemd.ts:254-279
  function parseFrontmatterPaths(rawContent: string): { content: string; paths?: string[] } {
    const { frontmatter, content } = parseFrontmatter(rawContent)
    if (!frontmatter.paths) return { content }
    const patterns = splitPathInFrontmatter(frontmatter.paths)
      .map(pattern => pattern.endsWith('/**') ? pattern.slice(0, -3) : pattern)
      .filter(p => p.length > 0)
    if (patterns.length === 0 || patterns.every(p => p === '**')) return { content }
    return { content, paths: patterns }
  }

  问题五：Permission、Sandbox 与 PreToolUse 的安全边界

  5.1 严格先后顺序

  从 checkPermissionsAndCallTool()（src/services/tools/toolExecution.ts:599）还原的完整顺序：

  1. Zod 输入校验 (line 615)
     ↓
  2. tool.validateInput() (line 683)
     ↓
  3. startSpeculativeClassifierCheck() — Bash 投机分类器 (line 741)
     ↓
  4. runPreToolUseHooks() — PreToolUse Hook (line 800)
     ↓  ← Hook 可返回 updatedInput、permissionDecision、block
  5. resolveHookPermissionDecision() (line 921)
     ├→ Hook allow → checkRuleBasedPermissions() → 规则 deny/ask 仍生效
     ├→ Hook deny → 直接拒绝
     ├→ Hook ask → 进入交互式审批
     └→ Hook passthrough → 进入正常权限流程
     ↓
  6. canUseTool() — 交互式权限审批 (line 921 内部)
     ├→ hasPermissionsToUseTool() — 规则检查
     ├→ classifier 检查（auto mode）
     └→ 用户交互（ask mode）
     ↓
  7. tool.call() — 实际执行
     ↓
  8. runPostToolUseHooks() — PostToolUse Hook

  5.2 PreToolUse 在用户批准之前还是之后

  之前。PreToolUse Hook 在 resolveHookPermissionDecision() 之前运行（toolExecution.ts:800 vs 921）。

  但 Hook 的 allow 不能绕过 settings.json 中的 deny/ask 规则：

  // src/services/tools/toolHooks.ts:373-391
  const ruleCheck = await checkRuleBasedPermissions(tool, hookInput, toolUseContext)
  if (ruleCheck === null) {
    // 没有匹配规则 → Hook allow 生效
    return { decision: hookPermissionResult, input: hookInput }
  }
  if (ruleCheck.behavior === 'deny') {
    // deny 规则覆盖 Hook allow
    return { decision: ruleCheck, input: hookInput }
  }
  // ask 规则 → 需要用户审批
  return { decision: await canUseTool(tool, hookInput, ...) }

  5.3 Hook 修改输入后是否重新校验

  是。Hook 返回 updatedInput 后，processedInput 被更新，后续的 resolveHookPermissionDecision() 使用更新后的输入进行规则检查。但不会重新运行 PreToolUse Hook。

  5.4 用户批准一次后重试

  如果参数变化，需要重新批准。如果参数相同，批准结果通过 permissionMode 的缓存机制（如 session 规则）复用。

  5.5 Shell 命令解析

  src/utils/bash/commands.ts 的 extractOutputRedirections() 处理管道和重定向。src/tools/BashTool/bashPermissions.ts 的 startSpeculativeClassifierCheck() 解析复合命令。

  5.6 子代理权限

  子代理不能扩大父代理的权限。runAgent.ts:466-479：

  // src/tools/AgentTool/runAgent.ts:466-479
  if (allowedTools !== undefined) {
    toolPermissionContext = {
      ...toolPermissionContext,
      alwaysAllowRules: {
        cliArg: state.toolPermissionContext.alwaysAllowRules.cliArg,  // 保留 SDK 级
        session: [...allowedTools],  // 仅使用显式允许的
      },
    }
  }

  5.7 Hook 权限

  Hook 以当前进程权限运行（spawn() 继承 env），没有独立的 Sandbox。Hook 可以访问 cwd、transcript_path、session_id 等信息。

  问题六：Stop Hook 验证闭环

  6.1 触发条件

  handleStopHooks()（src/query/stopHooks.ts:65）在模型产生最终文本后运行。从 query.ts 的循环逻辑推断，触发条件是：
  - 模型响应中没有 tool_use blocks
  - stopHookActive 不为 true（防止递归）
  - 不是用户中断、API 错误或 maxTurns 到达

  6.2 运行时机

  在模型产生最终文本之后，在返回给用户之前。

  6.3 阻止结束时的重新进入

  如果 Stop Hook 返回 blocking errors（src/query/stopHooks.ts:325-332）：

  if (preventedContinuation) {
    return { blockingErrors: [], preventContinuation: true }
  }
  if (blockingErrors.length > 0) {
    return { blockingErrors, preventContinuation: false }
  }

  blocking errors 作为 user message 注入消息历史，触发下一轮模型调用。

  6.4 防止无限阻止

  stopHookActive 参数（src/query/stopHooks.ts:73）传递给 executeStopHooks()，当为 true 时跳过 Stop Hook 执行。

  6.5 Stop vs SubagentStop vs SessionEnd

  是不同的事件。从 HOOK_EVENTS 列表确认：
  - Stop：主代理完成回复
  - SubagentStop：子代理完成（src/query/stopHooks.ts:334 的 isTeammate() 检查）
  - SessionEnd：会话结束（src/utils/hooks.ts:169-182，超时仅 1.5 秒）

  6.6 Stop Hook 能看到什么

  从 createBaseHookInput()（src/utils/hooks.ts:301-328）推断，Stop Hook 可以看到：
  - session_id
  - transcript_path（可读取完整 transcript）
  - cwd
  - permission_mode
  - agent_id / agent_type

  但不能直接看到本轮修改的文件列表、测试命令或退出码——这些需要 Hook 自己从 transcript 或文件系统中提取。

  6.7 Claude Code 是否真正验证 TDD

  推测：Claude Code 没有程序化验证"先有失败测试，再写生产代码"。这完全依赖：
  1. CLAUDE.md 中的提示词约束（"TDD 铁律"）
  2. 模型的指令遵循能力
  3. 用户/CI 的事后验证

  Stop Hook 可以近似验证（检查 transcript 中是否包含测试命令），但不能确定性地判断。

  6.8 flaky 测试区分

  推测：Claude Code 没有内置机制区分代码失败、测试基础设施失败和超时。Stop Hook 只能看到退出码和 stdout/stderr，需要自行解析。

  Permission/Hook/执行器边界

  HookRunner (扩展点) ←→ PermissionChecker (硬边界) ←→ ToolExecutor (执行器)
       ↑                        ↑                           ↑
    可 allow/deny/ask      deny 规则不可覆盖          唯一入口
    可修改输入              规则检查在 Hook 之后      所有路径汇聚

  子代理与主代理一致的 Hook/权限传播

  - 子代理继承父代理的 permission_mode
  - 子代理有独立的 agent_id
  - Hook 通过 agent_id 区分主代理/子代理调用
  - 子代理启动时 clearSessionHooks() 清除父代理的 session hooks

  Stop 验证闭环

  1. 修改 TypeScript 后没有运行测试 → Stop Hook 检查 transcript 中是否有 test 命令
  2. 测试失败却声称完成 → Stop Hook 检查最后的 tool_result 是否包含 is_error: true
  3. typecheck/lint 未运行 → Stop Hook 检查 transcript 中是否有 tsc/eslint 命令
  4. 子代理没有结构化 evidence → SubagentStop Hook 检查 stdout 内容
  5. Stop Hook 自身超时 → 默认 10 分钟超时，超时视为非阻塞错误
  6. 连续阻止上限 → stopHookActive 参数防止递归

  不应照搬 Claude Code 的部分

  1. 27 种 Hook 事件：micode 应从 5 种核心事件开始（PreToolUse、PostToolUse、Stop、SessionStart、SessionEnd）
  2. 异步 Hook 协议：{ async: true } 增加复杂度，micode 可先只支持同步
  3. PowerShell 支持：如果 micode 不需要 Windows 支持，跳过 shell 选择逻辑
  4. MCP 工具系统：如果 micode 不使用 MCP，跳过 MCP 相关的 Hook 逻辑
  5. classifier/auto mode：这是 Claude Code 特有的权限分类器，micode 可以不实现
  6. context collapse / snip compact：这些是高级上下文管理，初期不需要
  7. Perfetto tracing：性能追踪是可选的
