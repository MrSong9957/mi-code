  根因分析

  1. 没有 seq tiebreaker：源码中 timestamp: Date.now() 是唯一的排序依据，getHistory() 依赖文件行序而非 timestamp 排序。如果测试代码中确实有 seq tiebreaker，那是测试自己添加的——但核心模块不保证同毫秒稳定性。
  2. "期望 2 得 4"的根因是模块级状态泄漏：
    - pendingEntries、isWriting、cleanupRegistered、skippedTimestamps 都是模块级变量
    - addToHistory 第一次调用时注册 cleanup（src/history.ts:419-431）：
  if (!cleanupRegistered) {
    cleanupRegistered = true
    registerCleanup(async () => {
      if (currentFlushPromise) await currentFlushPromise
      if (pendingEntries.length > 0) await immediateFlushHistory()
    })
  }
    - clearPendingHistoryEntries()（src/history.ts:436-440）只清除 pendingEntries、lastAddedEntry、skippedTimestamps，不清除 cleanupRegistered、isWriting、currentFlushPromise
  3. USERPROFILE 劫持的隔离失效原因：
    - os.homedir() 在 Node.js 中缓存了首次调用结果（process.env.USERPROFILE 的快照）
    - getClaudeConfigHomeDir() 依赖 os.homedir() 返回 ~/.claude 路径
    - 即使重写 process.env.USERPROFILE，如果 os.homedir() 已被其他测试模块在 import 时求值过，后续调用仍返回旧值
    - 在 singleFork 模式下，所有测试共享同一个 Node.js 进程，模块缓存不会重置
  4. "期望 2 得 4"的具体机制：测试 A 写入 2 条 history 到 USERPROFILE_A/history.jsonl，测试 B 重写 USERPROFILE 为 USERPROFILE_B，但由于：
    - os.homedir() 缓存未更新 → 读的还是 USERPROFILE_A/history.jsonl
    - 或 pendingEntries 未完全 flush → 测试 B 的 getHistory() 还读到了测试 A 的 pending 条目

  修复方向

  问题 3：是否值得引入 vitest retry/flaky 缓解机制

  仓库现状

  - vitest.config.ts 不存在于本反编译仓库
  - package.json 中没有 vitest 依赖（只有 esbuild 和 typescript 作为 devDependencies）
  - 没有 setupFiles、testTimeout、retry 配置

  三类 flaky 的策略建议

  ┌──────────────────────────┬─────────────────────────────┬─────────────────────────────────────────────────────────────────┬───────────────────────────────────┐
  │        Flaky 类型        │            本质             │                            正确策略                             │             错误策略              │
  ├──────────────────────────┼─────────────────────────────┼─────────────────────────────────────────────────────────────────┼───────────────────────────────────┤
  │ 超时类（bootstrap-flag） │ 冷启动耗时不稳定            │ 测试自身加固：per-test timeout 提升到 15s                       │ 全局 retry（掩盖真实性能退化）    │
  ├──────────────────────────┼─────────────────────────────┼─────────────────────────────────────────────────────────────────┼───────────────────────────────────┤
  │ env 竞争类（history）    │ 模块状态 + homedir 缓存泄漏 │ 测试自身加固：vi.mock + clearPendingHistoryEntries() + 隔离 env │ retry（可能恰好通过，但根因未修） │
  ├──────────────────────────┼─────────────────────────────┼─────────────────────────────────────────────────────────────────┼───────────────────────────────────┤
  │ 真实 IO 时序类           │ 文件锁、flush 竞态          │ 测试自身加固：await flush 完成 + 重试写入断言                   │ 配置级容忍（IO 竞态是确定性 bug） │
  └──────────────────────────┴─────────────────────────────┴─────────────────────────────────────────────────────────────────┴───────────────────────────────────┘

  结论：不推荐全局 retry。 原因：
  1. 这三类 flaky 都有确定性根因，retry 只是掩盖
  2. Vitest 3.x 不原生支持 retry 配置（需要自定义 reporter 或 --retry CLI flag）
  3. retry 会让 CI 时间膨胀（每个 flaky test 最多跑 N 次）

  全局 testTimeout 建议值

  如果要加，建议 15000ms，依据：
  - env-scrub 测试已使用 15000ms timeout（用户提到的参考值）
  - Windows 冷启动模块求值 ~3-5s + Ink 渲染 ~1-2s + 安全余量 = ~10s 上限
  - 15s 留有 50% 余量，覆盖 Windows Defender 扫描等偶发干扰

  // vitest.config.ts 建议
  export default defineConfig({
    test: {
      testTimeout: 15000,
      // 不加 retry — 每个 flaky 应该被根治
    },
  })

  ├──────┼────────────────┼────────────┼──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤

  └──────┴────────────────┴────────────┴──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

  history 最该先修，因为：
  - 它的失败是非确定性的（每次不同用例），无法通过"再跑一次"绕过
  - 它污染了整个 test suite 的可信度（其他测试的失败可能是 env 泄漏导致）
  - 修复它同时修好了测试隔离基础设施，收益最大

  regression 目录状态

  本仓库无 regression 浮试目录（反编译已剥离）。但从用户描述（11 个测试含 it.fails）推测：
  - it.fails 是 vitest 的"期望失败"语法，用于标记已知 bug
  - 如果 it.fails 的测试偶尔通过（即不再 fail），它也会变成 flaky
  - regression 测试通常是稳定的（它们验证已修复的 bug 不回归），但如果依赖外部状态（文件系统、env），也可能成为 flaky 源

  测试金字塔薄弱层

  基于用户描述的规模（agent 83、tui 62、regression 11，共 ~295 文件）：

  ┌──────────┬──────────────────────────────────────────────────────┬───────────────────────────────────────────────────────────────────────┐

  ├──────────┼──────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────────────────┤
  │ 集成测试 │ tui 62 个测试覆盖 Ink 渲染 + setup 流程              │ 最薄弱——重 IO、冷启动、真实 stdout 写入，是 flaky 的主要来源          │
  ├──────────┼──────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────────────────┤
  │ E2E 测试 │ agent 83 个测试可能覆盖端到端流程                    │ 依赖 mock 程度未知                                                    │
  └──────────┴──────────────────────────────────────────────────────┴───────────────────────────────────────────────────────────────────────┘

  最薄弱层是集成测试（tui 目录），因为：
  - 它混合了真实渲染（Ink）和真实 IO（stdout、文件系统），既不是纯单元也不是纯 E2E
  - bootstrap-flag 测试就是典型：它想验证 flag 逻辑，却不得不启动整个 TUI 引擎
  - 建议：将 flag 逻辑提取为纯函数单独测试，TUI 集成测试用 vi.mock 减少 IO 依赖
